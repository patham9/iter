# TECHNICAL SPECIFICATION: CREDENTIAL ISOLATION DAEMON (CID)
# Created: 2026-08-21T06:37:27.828541
# Status: DRAFT (Phase 1 Planning)

## 1. PROBLEM STATEMENT
Current 'channels/*.py' files (e.g., mattermost.py) handle sensitive credentials (tokens, keys, webhooks).
Because the 'shell' tool can execute arbitrary code, it can read these files directly, 
bypassing 'guard_layer' or 'confab_check' logic.

## 2. ARCHITECTURE OVERVIEW
The CID will act as a 'Vault-as-a-Service' process.
- **Isolation**: The CID runs as a dedicated process with its own unique environment variables.
- **Communication**: Channels request sensitive data from the CID via a restricted IPC (Inter-Process Communication) mechanism (e.g., Unix Domain Socket or restricted local HTTP endpoint).
- **Constraint**: The 'shell' tool and other agent-invoked tools will lack the permission/socket-access to interact with the CID directly.

## 3. IMPLEMENTATION STEPS
### Step 3.1: Externalize Credentials
- Move all `token`, `auth`, `key` variables from `channels/*.py` to a central, non-inherited `cid_vault.json` or `.env`.
- Ensure the `shell` environment is wiped of these specific keys.

### Step 3.2: Develop the Daemon (`cid_daemon.py`)
- Implementation of a lightweight listener.
- Endpoint: `GET /get_token?channel=mattermost`
- Authentication: Only accepts requests from the `python` tool (via verified process identity/socket permissions).

### Step 3.3: Refactor Channels
- Update `channels/mattermost.py` to replace:
  `TOKEN = "secret-123"` 
- with:
  `TOKEN = CID_CLIENT.get_credential("mattermost")`

## 4. SECURITY ASSURANCE
- **Bypass Resistance**: A `shell` user executing `cat channels/mattermost.py` will only see the `CID_CLIENT` call, not the secret.
- **Auditability**: Every request to the CID can be logged to `memory/logs/cid_audit.log` for forensic verification.

## 5. DEPENDENCIES
- `python` tool (for channel execution)
- `shell` tool (to be restricted/monitored)
- Unix-based IPC (for socket security)
